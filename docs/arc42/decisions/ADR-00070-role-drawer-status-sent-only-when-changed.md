## 背景

- 005 刀接真之角色抽屜（`base-web/src/views/manage/role/modules/role-operate-drawer.vue`）編輯既有角色時，handleSubmit 之更新分支恆送表單現值之 `status`（`status: model.value.status ?? undefined`）。表單於開啟時由 `props.rowData` 逐欄回填；`rowData` 是清單頁點擊編輯當下以 `jsonClone` 複製之列快照（`base-web/src/hooks/common/table.ts` 之 `handleEdit`），開啟期間不重取。
- 後端 updateRole 之停用雙護欄（ADR-00044 決定 3）依 005 刀 contracts §4⑤ 所定口徑，以「請求 `status` 出現且解析為停用」觸發、不比對現值（`rust-api/server/src/handler/role.rs` 之 `update_role_in_txn`：`update.patch.status.is_some_and(|status| status != STATUS_ENABLED)` 才查成員身分與 R_SUPER）。
- 兩者合成 BL-00131 之兩失效面：
  - **①停用雙護欄誤擋**：操作者所屬之已停用角色，經抽屜只改名稱或描述送出 → 請求帶回填之停用值 → `biz.role.cannotDisableSelfRole`。seed 之 `sys_user_role` 三列各一人一角色、持 R_SUPER 之帳號恰 1 且只屬 R_SUPER、尚無使用者角色指派寫端 ⇒ 現況生產面不可達；指派寫端落地（使用者域刀）後可達。
  - **②兩分頁舊值覆寫**：同一帳號兩分頁或兩裝置同開（`single_session_default`＝off 允許多會話）；乙分頁停用某角色後，甲分頁以開啟時快照只改名稱送出 → 帶回填之啟用值 → 啟用不觸護欄、成功 ⇒ 乙之停用被靜默撤回（停用即斷權一併撤回）。現況可達；本刀使 updateRole（seed 政策 protected＝FALSE、屬 21 支可授出端點）可經端點維授予非超管後即成跨人情境。
- rev5 抽屜同形恆送、無藍本可承。rev6 之 updateRole 請求型 `Api.RoleAdmin.RoleUpdateReq` 之 `status` 本即可選；缺席＝不動（ADR-00047 決定 2 之「非三態欄之 null＝缺席」與決定 4 之狀態類欄值域收斂）。
- brainstorm §0 Q9 裁本刀前端修；Q5 裁停用雙護欄不入島 G 條文、保留後端修法彈性。

## 決策驅動因子

- 兩失效面一次消除，且後端口徑、契約與其釘案零改。
- 改點落在既有授權內：不增修改型、不增圈界塊、不動憲法 §III.2 範圍欄 ⇒ 免 §V.2 Amendment。
- 行為可機器觀察（CDP 網路請求事件）、與 rev5 之差異可逐項登記。
- 不預占後端護欄之後續修法（Q5）：日後若改轉移觸發，本前端修仍成立、不衝突。

## 考慮過的替代案

1. **後端只在「啟用→停用」轉移時觸發**（BL-00131 選項一；鎖內比對變更前狀態）：消除誤擋，但**不消除舊值覆寫**——甲分頁帶的是啟用值、啟用本不觸護欄，覆寫照舊成功；且須翻 005 刀 data-model §5.2⑤ 與 contracts §4⑤ 之口徑及其釘案（`handler/role.rs` 測試模組之 `disable_guards_refuse_self_role_before_super_and_count_disabled_memberships` 釘「掛著已停用之自建角色、再送停用＝`cannotDisableSelfRole`」），並須另立 ADR 翻該口徑（ADR-00044 決定 3 未定觸發形、且 accepted 後 body 不可變）。否決。
2. **開啟抽屜時重取角色**（治標舊值覆寫）：把舊值窗縮到「開啟→送出」之間，但**不治雙護欄誤擋**——重取得到的仍是停用值、照送照擋；rev6 角色域無以 id 取單一角色之讀端（讀端＝getRoleList〔名稱、代碼子字串與狀態篩選，無 id 篩選〕、getAllRoles、getRoleHome），重取須經清單讀端篩選再逐列比對、或新增端點（新端點＝新 seed 政策列、牴觸本刀零 seed 變更）；且改點落在開啟流程（upstream 之 `watch(visible)`／`handleInitModel`）、溢出既有圈界＝(ii) 範圍欄塊數變動、須隨 Amendment 實數化。否決。
3. **維持 rev5 恆送**：CDP 零分岔，但兩失效面照留，舊值覆寫隨本刀授權下放成跨人可達。否決。
4. **只送變動欄（名稱、描述、備註亦改為異於回填值才帶）**：連同殘餘②一併處理，但超出 Q9 裁定射程（狀態欄），且改變 operator 可見行為——未改任何欄即按確定，現為一筆 `update` 稽核，改後全欄缺席＝提前 no-op（成功、零變更、零稽核；ADR-00047 決定 3）＝拍板級。否決（列翻案觸發器）。

對所選方案跑同一反例（RL-0013）：①「乙分頁停用、甲分頁只改名稱」→ 甲請求不帶 `status` → 後端不動狀態 → 乙之停用存續，成立。②「操作者所屬已停用角色只改名稱」→ 不帶 → 護欄不觸發 → 名稱落地，成立。③「操作者真要停用自己所屬角色」→ 狀態由啟用改停用＝異於回填值 → 帶 → 護欄照擋，護欄保護力不減，成立。④「甲開啟時為停用、乙改啟用、甲把狀態改為啟用再改回停用後送出」→ 終值＝回填值 → 不帶 → 乙之啟用存續；甲之淨意圖為「狀態不變」、結果與之相符，成立。⑤「甲開啟時為啟用、乙改停用、甲明示把狀態改為停用後又改回啟用、再改名稱送出」→ 終值＝回填值 → 不帶 → 乙之停用存續；反之甲終值異於回填值者必為甲在表單上明示改動之結果、照送，屬後送出者覆蓋（見後果殘餘①），非本修法所防之靜默覆寫。成立。

## 決定

1. **判準**：角色抽屜編輯既有角色、送出 updateRole 時，`status` 只在表單現值與**開啟時回填值**不同時才帶；相同＝請求 body **不含 `status` 鍵**（非 `null`、非空字串；後端依 ADR-00047 決定 2／決定 4 視同缺席＝不動）。開啟時回填值＝抽屜 `rowData`（清單頁點擊編輯當下之列快照、開啟期間不變）之 `status`。名稱、描述、備註三欄照舊逐欄送（不在本 ADR 射程）；新增角色路徑照舊帶 `status`。
2. **改點與授權**：只改 handleSubmit 送出塊之更新分支——該塊位於用途 (ii) 既有新增型圈界 `[rev6-inline BASE-WEB-MANAGE-PAGE-WIRING(ii)+ 005-role-menu-crud START]`…`END` 之內；圈界兩標記行一字不動（刀名欄記的是該塊之開立刀；`tools/fork-delta-lint.py` 對新增型只驗 token 在場）；不新增修改型、不新增圈界塊 ⇒ 憲法 §III.2 (ii) 列範圍欄之本檔處數（以該列現文為準）不變，且屬該列紀律欄「新增編輯 drawer」接真之射程內修正 ⇒ **免 §V.2 Amendment**。同檔之第三鈕屬用途 (iii) 新增型、由 ADR-00063 決定二之 Amendment 授權，與本決定分計。塊內說明註解同批改寫（現句「狀態已過必填規則、`?? undefined` 只為收窄型別」於修後失真；RL-0011 種子）。wire 型別零變更（`Api.RoleAdmin.RoleUpdateReq` 之 `status` 本即可選）。免修憲僅指授權面；施工時序仍受本刀「ADR-00063 accepted 前 base-web 既有檔零 diff」硬序約束（spec US5 AS1），落點隨角色抽屜接線單元。
3. **兩失效面之消除論證**：
   - **①誤擋**：只改名稱或描述時狀態等於回填值 → 請求無 `status` → `update_role_in_txn` 之護欄條件（`status` 出現且非啟用）不成立 → 不查成員身分、不擋 → 名稱落地。操作者真改為停用時請求照帶、護欄照判，保護力不減。
   - **②舊值覆寫**：甲分頁只改名稱時狀態等於其開啟時快照 → 請求無 `status` → 後端不動狀態欄 → 乙分頁於其間寫入之狀態存續；甲以舊快照覆寫狀態之路徑自此只剩「甲明示改動狀態」一形（決定 1 之判準使其必為異於回填值者），屬明示意圖之後送出者覆蓋、非靜默覆寫。
4. **後端不動**：停用雙護欄（ADR-00044 決定 3）於 005 刀 contracts §4⑤（data-model §5.2⑤ 同口徑）所定之觸發口徑——請求 `status` 解析為停用即判、不比對現值——與其釘案零改；UI 外呼叫端對已停用之自身所屬角色再送停用值照擋＝by-design。保留 Q5 所留之後端修法彈性：日後若改為轉移觸發，另立 ADR，本決定照常成立。
5. **刻意分岔與 CDP 對照**：與 rev5 HEAD（恆送）之分岔登入本刀 spec 刻意分岔登記表（FR-035、FR-053），並自 SC-010 結構清單全等之比對面排除（SC-010 排除清單含該表各項）；rev6 側（32080）另以網路請求事件單邊斷言兩案：只改名稱送出 → updateRole 請求 body 無 `status` 鍵；改動狀態送出 → 帶 `status` 且值＝新選值。base-web 無前端單元測試執行器（`package.json` 無 test 腳本、零 vitest／jest 依賴），本行為之機器觀察面＝此 CDP 斷言（前端型別檢查綠只擔保型別，不觀察送出欄集）。
6. **帳本**：BL-00131 於本刀收刀以 `backlog_done` 刪列（FR-046）；殘餘面記於本 ADR 後果（其已知態之承載＝ADR-00068 款 11、候選丙、候選丁）、附翻案觸發器，不另立 BL。本 ADR 後果以 ADR-00068 候選丙／候選丁為錨 ⇒ accepted 不早於治理單元對該兩候選定案；定案同顆把本檔決定 6 與後果之候選名改寫為所配款號，或刪去該引用（ADR-00068 決定 3）。觀察記錄：候選丙已於 006 刀 U16 CDP 實測屬實（兩分頁下後送出者以開啟時舊名覆寫、前端無衝突提示）；候選丁以既有整合測試釘案為觀察記錄；兩者定案待治理單元。決定 1／決定 2 為憲法 §III.2 (iii) 列紀律欄所引（ADR-00063 決定二），於本 ADR accepted 前 MUST NOT 改動（ADR-00063 翻案觸發器之「同一親決輪先定…或被 §III.2 (iii) 列紀律欄指向之 ADR-00070 決定 1／決定 2」條；確需改動＝停手升級）。

## 後果

- BL-00131 兩失效面於本刀消除；就本修法而言：rust-api 零碼改、契約與釘案零改，base-web 改動限一檔一塊之塊內行，fork-delta 範圍欄與 wire 快照不因之變動。
- 殘餘①：兩分頁**皆改狀態**時為後送出者覆蓋（明示意圖之 last-writer-wins；抽屜無樂觀鎖）——與授權彈窗「並行編輯後送出者覆蓋」同型（其已知態＝ADR-00068 款 11）。
- 殘餘②：名稱、描述、備註三欄仍恆送開啟時表單值 ⇒ 兩分頁下此三欄之舊值覆寫照舊（005 刀起既有、BL-00131 射程外；其已知態＝ADR-00068 候選丙；改法見替代案 4、屬拍板級）。
- 殘餘③：誤擋面之後端口徑未改 ⇒ 繞過 UI 直打 API、對已停用之自身所屬角色送停用值者照被擋（決定 4 by-design；其已知態＝ADR-00068 候選丁）。
- CDP 走查多一項 rev6 側單邊斷言（網路請求事件）；22080 側恆帶屬已登記分岔、不計差異。

## 翻案觸發器

- 後端停用雙護欄改為轉移觸發（另立 ADR）→ 複核本決定是否仍需（舊值覆寫面仍由本決定承擔，預期保留）。
- 抽屜改為開啟時重取、或 updateRole 引入樂觀鎖（版本欄或更新時戳比對）→ 舊值覆寫之論證改由該機制承擔、重審決定 1 與決定 3②。
- upstream rebase 改動角色抽屜之送出流程或表單模型（`status` 欄型別、回填方式、`handleEdit` 之列快照語意）→ 重驗判準落點仍在既有圈界內、開啟時回填值仍不隨清單刷新而變。
- 使用者角色指派寫端落地（使用者域刀）→ 誤擋面轉生產面可達；以端到端或 CDP 實測驗本修法仍使只改名稱之請求不被擋。
- 殘餘②之誤蓋實際發生、或出現第二個可編輯角色之人 → 重審名稱、描述、備註三欄是否同改「異於回填值才帶」（連帶提前 no-op 之稽核語意、屬拍板級）。
