## 背景

現有管理清單端點全部是伺服器寫死的穩定排序、以主鍵或唯一鍵決勝：IP 規則依 id 降冪；角色依 id 升冪；選單依 `order` 升冪（NULLS LAST）再依 id；已刪選單依 `deleted_at` 降冪再依 id 降冪；系統設定依 `setting_key` 升冪。請求查詢結構只有分頁欄（`current`／`size`）與篩選欄，零排序欄；base-web 管理頁零表頭排序。

BL-00044 字面只承載「設定清單排序」，事實上卻是 rev6 唯一承載「列表排序能力」的地方（前代 `rev5:B-027` 未帶進 rev6 任何現在式面）；004 刀 spec 泛指該條、005 刀 spec 無指針，承載已分裂。006 的 policy-archive 清單依 rev5:006 前例亦為固定序、契約零排序參數，006 spec 只需要在 Out of Scope 有個可指的承載。

## 決策驅動因子

- 006～008 spec 的 Out of Scope 需要單一、可指的承載。
- 前代全代零排序需求（`rev5:B-027` 至收官未觸發）；rev6 各清單、各頁面也零消費者。
- 排序參數、排序欄白名單（三端單一來源）與逐欄索引評估是新能力面，沒有消費者時不預先建。

## 考慮過的替代案

1. **條文放寬為泛列表排序、續掛 BACKLOG**——義務續佔開放帳、沒有自然到期點；否決（user 2026-09-29 裁定①）。
2. **維持現狀（設定排序隨 008、泛排序交 006 brainstorm）**——承載續分裂、006 spec 沒有單一指針；否決。
3. **提供排序（參數＋白名單＋索引）**——無消費者的新能力面；否決。

## 決定

1. 管理清單端點（現為 IP 規則、角色、選單、已刪選單、系統設定；後續新清單同）一律伺服器端固定穩定序、以主鍵或唯一鍵決勝；請求不收 client 排序參數；base-web 管理頁不設表頭排序。
2. 新清單端點的固定序由其刀 spec 定、同刀寫進契約；不另設排序參數。
3. `docs/arc42/08-crosscutting-concepts.md`「清單分頁通則」段載明本通則並指向本 ADR；006～008 spec 之 Out of Scope 指本 ADR。

## 後果

- 正面：列表排序之承載單一化、BL-00044 結案；零碼改。
- 負面：使用者點表頭不排序（行為不變）；有需求時須翻案本 ADR 並新建排序能力。

## 翻案觸發器

- 任一刀 brainstorm 或 user 提出具體排序需求（含欄位與使用情境）。
- 單一清單資料量成長到固定序無法支撐查找（以實際使用回報為準）。
