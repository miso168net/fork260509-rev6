## 背景

- 使用者批次刪除端點（`batchDeleteUser`）把請求之 id 去重後，於同一交易內逐 id 先取 advisory 鎖，全部取完才逐 id 鎖列並驗存在（不存在之 id 亦先佔鎖）；端點不限一次送幾個 id。`PAGE_MAX_SIZE`（100）只管分頁 clamp、與批刪無關。
- PostgreSQL 之鎖表全庫共用、容量有限（compose 之 postgres 未調鎖表參數、取預設）。一次送入數萬個 id 可佔滿鎖表：該次請求整批回滾、回 `5000`；佔滿期間其他連線（含登入要取之帳號鎖）取鎖亦可能失敗（機械推論、未實測）。
- 呼叫者限於持「使用者刪除」權限者：seed 預設只有 `R_SUPER`，006 刀起可經端點權限彈窗授出。
- 畫面前提：表格每頁筆數上限 30（`pageSizes`＝10／15／20／25／30）；勾選跨換頁保留——回收桶開關切換與批刪成功時清空、單刪成功只移除該筆——從畫面跨頁累積勾選亦能送出超過 100 筆。
- 007 刀規劃時把此點判為已知態，但只寫在該刀 research（凍結史料面），所載「畫面一次最多一頁 100 筆」之前提有誤；ADR 與活書 11 技術債表皆未登記（RL-0074：by-design 亦立 ADR）。

## 決策驅動因子

- 現行呼叫者限於持刪除權者，運維上之批量遠小於鎖表容量。
- 加上界即新增拒因（使用者可見）：跨頁累積勾選超過上界之批刪被拒，須補前端提示、三語譯文、msg-key 名冊、wire 契約與 rust 測試，並改 007 FR-014 之整批語意。
- 承載須落在現在式面：下輪審查再報此點時，須查得到單一出處。

## 考慮過的替代案

1. **加批量上界**（例：去重後超過 100 即回新拒因、零鎖零交易）：使用者可見行為變更、改 007 契約形、需容器 cargo。棄。
2. **併入 BL-00147**（資源耗用上界題、隨其滯後）：把 by-design 已知態改當待修缺陷，與 RL-0074 之「已知態立 ADR」路線不同。棄。
3. **行為不變、立 by-design ADR 並於活書 11 補指針**（選）。

對所選方案跑同一反例（RL-0013）：「非超管角色取得刪除權後以 API 直送超大批、拖垮他連線取鎖」——授出為顯式行政動作，且此形列為翻案觸發器首條；「下輪審查再報同點而查無承載」——決定 3 之活書 11 指針即現在式承載。成立。

## 決定

1. **行為不變**：batchDeleteUser 不設批量上界；超大批耗盡共用鎖表時整批回滾、回 `5000`（既有整批交易語意承擔，零部分刪除）。
2. **畫面前提**以本 ADR 背景為準（每頁上限 30、勾選跨頁保留）；007 刀 research 之「一頁 100 筆」屬凍結史料、不改。
3. 活書 11 技術債表「使用者域與繁中 runtime by-design 已知態」列增一款指向本 ADR。

## 後果

- 持刪除權者送超大批時，該次批刪整批失敗（`5000`）；鎖表佔滿期間其他取鎖之請求可能連帶失敗（機械推論、未實測）。
- 零碼改、零 migration、零 pin bump。

## 翻案觸發器

- 非超管角色取得 batchDeleteUser 政策（`/systemManage/batchDeleteUser`、seed 政策列 20；經端點權限彈窗授出即成立）⇒ 評估加批量上界或分批處理。
- 出現鎖表耗盡之實際事故，或出現以 API 直連之用戶端（非管理頁）呼叫本端點 ⇒ 同上。
- 007 FR-014 之整批語意變更 ⇒ 複核本 ADR。
