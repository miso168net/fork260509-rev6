## 背景

- updateMenu 內層（`handler/menu.rs` 之 `update_menu_in_txn`）之固定序：③入選單序列化域 → 鎖標的列（查無或已軟刪＝`notFound`）→ ④不可變欄出現即拒 → ⑤受保護選單列之停用或改父＝`biz.menu.protectedMenu` → ⑥父驗證與防環 → ⑦常量父鏈 → ⑧href 形制 → ⑨按鈕碼清單形制 → ⑩絕版碼（`sys_menu::obsolete_codes`：本次移除之碼中、治理域其餘選單皆不持有者）之按鈕維授權跨全角色移入歸檔（`menu_button_removed`、不可復原）→ ⑪寫列 → 稽核 `update`；回實際歸檔列數＝判定面同步之門。
- ⑤之受保護選單守門只看「停用」與「改父」，不看按鈕清單。m0003 之前按鈕維受保護列為零，⑩不可能觸及受保護列；m0003（ADR-00085）後 R_SUPER 名下 `role:add`／`role:edit`／`role:delete`／`menu:add`／`menu:edit`／`menu:delete` 六列受保護。
- **第二條自鎖路**（brainstorm R10）：超管於選單頁編輯 `manage_role`，自其按鈕清單刪掉 `role:edit`（或改碼）⇒ 該碼全域絕版 ⇒ ⑩把 R_SUPER 之受保護列移入歸檔（不可復原）⇒ 角色頁編輯鈕消失、三顆授權彈窗不可達＝無 UI 回復路徑。此即以執行期寫端變更受保護集，與島 G 之 G2 末句「受保護集之變更屬 seed 基線層級決策」相悖。
- 現況量測（2026-10-05；m0003 後之 seed）：受保護按鈕碼六枚所在選單恰兩列——`role:*` 在列 4 `manage_role`、`menu:*` 在列 5 `manage_menu`，兩列 `protected`＝TRUE（島 H3：不可刪、不可停用、不可改父）；其餘選單之按鈕清單不含此六碼。
- 選單刪除家族（刪除、批刪）之連動歸檔亦會掃該選單「獨有」之按鈕碼（`menu_soft_delete`）；受保護選單本身已由 ⑤ 同族守門擋刪。

## 決策驅動因子

- 封住第二條自鎖路；受保護集不得經任何執行期路徑改變（G2）。
- 拒在任何寫入之前、整筆拒、不靜默壓縮（不得剔除受保護列後照歸其餘）。
- 判定位次與拒因不與既有守門互吞（一因一鍵）。
- 單一掛點、判定只依本次請求與受保護列，不依其他選單之當下狀態（避免多步繞道）。

## 考慮過的替代案

1. **判定集取「絕版集」（只在全域絕版時才擋）**：多步繞道——先把 `role:edit` 加到某非受保護選單 M2、再自 `manage_role` 移除（非絕版、放行）、再刪 M2（`menu_soft_delete` 掃 M2 獨有碼＝歸檔 R_SUPER 受保護列）⇒ 自鎖；須另掛刪除家族。否決。
2. **⑩照跑但略過受保護列**（只歸非受保護列、受保護列留現役）：留下指向「已無選單持有之碼」之受保護列＝候選外現役列、UI 看不見也撤不掉；屬部分成功之靜默壓縮、反轉 H2 之「同理歸檔」語意。否決。
3. **只在前端擋**（選單抽屜不讓刪受保護碼）：前端非權威、直打 API 照過（後端單一真源）。否決。
4. **把受保護選單之按鈕清單整體鎖死**（擴 ⑤ 至任何按鈕清單變更）：過寬——增碼、改說明亦被擋；且不擋「受保護碼在非受保護選單」之形。否決。
5. **沿用 `biz.role.protectedRevoke`**：該鍵屬角色域授權寫端、語意為「撤銷集觸及受保護列」；本守門在選單域、對象為按鈕碼移除；一因一鍵（FR-004）。否決。
6. **位次緊接 ⑤**（物理上與受保護選單守門相鄰）：須在 ⑨ 形制檢查之前解析按鈕清單，壞形清單之拒因會被本守門搶先或須雙處理。否決（取 ⑨′）。

對所選方案跑同一反例（RL-0013）：
- 替代案 1 之多步繞道：第二步自 `manage_role` 移除 `role:edit` ⇒ 移除集含受保護碼 ⇒ 整筆拒。成立。
- 改碼（`role:edit`→其他字面）⇒ 舊碼入移除集 ⇒ 拒；清空清單（`buttons` 為 null）⇒ 全部舊碼入移除集 ⇒ 拒。成立。
- 刪 `manage_role`／`manage_menu`（含批刪夾帶）⇒ ⑤同族受保護選單守門整筆或整批拒。成立。
- 刪「也持有受保護碼」之非受保護選單 M2 ⇒ 該碼仍在受保護選單內、非 M2 獨有 ⇒ 不歸檔。成立（前提：受保護碼恆在受保護選單之清單內，見決定 6）。
- 判定與寫入之間受保護列被改？受保護旗標無執行期寫端、受保護列之撤銷整批拒、R_SUPER 受 seeded 守門擋刪 ⇒ 交易期間不變；判定仍於域內鎖標的列之後現查。成立。

## 決定

（草稿；user 親決於 U0 施工前提顆；親決輪後依結果改寫本節並補親決紀錄。）

1. **判定集與時點**：updateMenu 請求之 `buttons` 欄出現時，於 ⑨（按鈕碼清單形制）之後、⑩（絕版碼歸檔）之前（記為 ⑨′）判：移除集＝標的寫前之碼 − 請求之碼（`button_codes_of` 之去重形；`buttons` 為 null＝寫後無碼、舊碼全數入移除集；改碼＝舊碼入移除集）；移除集 ∩「持有受保護按鈕維授權列之碼」≠ ∅ ⇒ 整筆拒。
   - 「持有受保護按鈕維授權列之碼」＝`casbin_rule` 中 `ptype='p' ∧ v2='button' ∧ protected=TRUE ∧ v1 ∈ 移除集` 之 `v1` 集；不問 `v0`、不濾角色狀態（同 ADR-00064 決定 1 不問 `v0` 之理：誰持有不影響「該碼受保護」）。單次查詢、不另取鎖（域內、標的列鎖之後；受保護列交易期間結構上不變，見反例末條）。
   - 承載件：移除集算法自 `sys_menu::obsolete_codes` 抽出為純函式 `sys_menu::removed_codes`（`obsolete_codes` 改呼之、兩處同一移除集定義）；查詢件新建 `sys_casbin_policy::protected_button_codes`（`casbin_rule` 讀面之家、與 `protected_endpoint_set` 同檔；以參數收碼集）。不新增名冊閘腿（呼叫點由測試承載、決定 7 之變異自證）。
2. **拒因與效果**：`2222`＋`biz.menu.protectedButtonRemove`（純 key、`data` null、不指出是哪個碼；FR-004）；判定在任何寫入之前 ⇒ handler 收場 rollback ⇒ 零變更（選單列、授權表、授權歸檔表）、零稽核、零判定面同步（未 commit、未達歸檔）。前端走既有錯誤提示（純 key toast、無明細）。
3. **位次與不互吞**：固定序變為 ③入域 → 鎖列 → ④不可變欄 → ⑤受保護選單 → ⑥父與防環 → ⑦常量父鏈 → ⑧href → ⑨按鈕碼形制 → ⑨′本守門 → ⑩絕版碼歸檔 → ⑪寫列 → 稽核；多重違規取先序腿。「與受保護選單守門並列」＝兩支獨立守門、拒因分鍵：⑤管受保護選單列本身之停用與改父，⑨′管任一選單之按鈕碼移除是否觸及受保護授權（標的不限受保護選單）。
4. **射程**：只掛 updateMenu。addMenu 只增碼、restoreMenu 不減碼（復原不回灌，H5）、刪除家族之受保護選單已由 ⑤同族守門擋刪、角色域撤銷由 G2 之 `biz.role.protectedRevoke` 擋——皆不另掛。
5. **與憲法之關係**：本守門承島 G 之 G2 末句（受保護集只在 seed 基線層變更）、為島 H2「編輯致全域絕版即歸檔」之前置守門；島 H2 是否補「選單編輯移除之按鈕碼尚有受保護授權＝整筆拒」一句由 ADR-00074 親決輪定——補句＝本守門升為入憲不變式（反轉＝MAJOR），不補＝本 ADR 為唯一承載；兩種結果下本 ADR 決定 1～4 不變。
6. **前提與已知態**：
   - 前提＝凡持有受保護按鈕維授權列之碼，皆在至少一列受保護選單之按鈕清單內（m0003 後：`role:*`⊂`manage_role`、`menu:*`⊂`manage_menu`）——使選單刪除家族之「獨有碼」歸檔恆不及受保護列。
   - 已知態：受保護碼若被加到某非受保護選單 M2 之清單，此後無法以編輯把它自 M2 移除（⑨′照判移除集、整筆拒）；只能刪 M2（該碼仍在受保護選單內、不歸檔）。屬本守門取「移除集」而非「絕版集」之刻意代價（替代案 1）。
7. **測試（FR-043、FR-063、SC-007）**：
   - 負向（合成、不依賴 seed 演進）：測試件直種一列非 seed 合成選單（帶合成碼）＋一列以該碼為 `v1` 之受保護按鈕維授權列 ⇒ 編輯移除該碼 ⇒ `biz.menu.protectedButtonRemove`、選單列不變、授權表與歸檔表以水位窗計零變更、稽核以水位窗計零列、判定面同步計數不增；改碼與清空清單兩變形各一案。
   - 負向（seed、m0003 後）：編輯 `manage_role` 移除 `role:edit` ⇒ 同上拒（US4 AS11；拒＝零變更、不留 seed 列變更）。
   - 正向：移除不持受保護授權之碼 ⇒ 照常寫入並依絕版與否歸檔（既有案不變）；`obsolete_codes` 抽出後之既有釘案全綠。
   - 位次一案：同一請求兼具受保護選單之停用與受保護碼移除 ⇒ 回 `biz.menu.protectedMenu`。
   - 變異自證：拆掉 ⑨′ 之呼叫或改其判定集 ⇒ 負向案轉紅（紅證印 skipped=0）⇒ 還原 ⇒ 綠。
8. **msg 鍵同批面**：`msg_key::BIZ_MENU_PROTECTED_BUTTON_REMOVE`＝`"biz.menu.protectedButtonRemove"`、`MSG_KEYS` 名冊、三檔 locale backend 子樹、`app.d.ts` backend 型節同單元落地（U4）；契約測試之真 seed 應用面實際發出（名冊雙向閘）；三語譯文措辭由本刀 contracts（msg-keys）定（繁中依 ADR-00084 之 zh-tw-lint）。

## 後果

- 第二條自鎖路封住：UI 上不存在使超管失去 `role:edit`（或其餘五碼）之路徑（與 ADR-00085 之第一路合成 SC-007 之「無路徑」主張）。
- 受保護按鈕維授權列經選單域路徑進入授權歸檔之案數恆零——ADR-00064 決定 4②（受保護授權列不進可復原歸檔）與 ADR-00044 決定 4 之 won't-use 分析續有效。
- 選單頁：編輯受保護選單（含 `manage_role`／`manage_menu`）時仍可改名、改圖示、增碼、改說明；移除受保護碼即 toast 拒。
- 與 rev5 HEAD 之差（rev5 照常移除並連動歸檔）入刻意分岔登記；CDP 對照排除此差。
- 新拒因鍵一枚（MSG_KEYS 名冊隨本刀新鍵同批增）；選單域寫端之判定增一次單表查詢（治理 QPS≈0、成本可忽略）。
- 現在式假述之同單元改寫（RL-0011；處數以 `python3 tools/docsync errata <詞>` 現算）：`update_menu_in_txn` 之固定序 doc、活書 06／08 之選單域編輯序與島 H2 情境句、選單域契約之固定序列舉（現在式面者）。

## 翻案觸發器

- 以 seed／migration 新增受保護按鈕維授權列而其碼不在任何受保護選單之清單內（決定 6 前提破）⇒ 複核本 ADR 是否擴掛刪除家族、或改判定集。
- 受保護旗標開放管理介面（島 G2 反轉＝MAJOR）⇒ 本 ADR 隨 G2 複核。
- 決定 6 之已知態成為實際問題（受保護碼誤加他選單而無法移除）⇒ 評估改採「絕版集＋刪除家族同掛」（替代案 1 之補全形）。
- 新增會移除按鈕碼之寫端（例：批次按鈕編輯、選單匯入覆蓋）⇒ MUST 掛同一判定（`sys_menu::removed_codes`＋`sys_casbin_policy::protected_button_codes`）並以新 ADR 更新決定 4。
- 島 H2 Amendment 採補句或其後被反轉 ⇒ 依決定 5 同步本 ADR 之承載定位。
