LL-00071｜analyze 報需求覆蓋 100％，逐子句稽核卻揭出 253 個子句只有部分斷言或零斷言——task 層追溯表只證「有掛 task」、不證「task 行內有斷言」（007 刀 SDD 後、實作前；2026-10-06）

**徵狀**：
- `/speckit-analyze` 對 007 刀報需求覆蓋 100％（每條 FR／SC／US 驗收場景都對到至少一支 task）、零 CRITICAL；tasks.md「需求追溯」表逐列有 task。
- user 2026-10-06 裁定逐子句全量稽核（唯讀、三 run）：驗收場景 50＋SC 14 拆 360 子句、FR 66 拆 711 子句、Edge Cases 52 拆 221 子句；每子句須指出 task 行內逐字錨、且錨屬五種斷言之一（測試案、機器守、演練走查、CDP 結構清單項、既有測試）。
- 結果：1292 子句中 253 個只有部分斷言或零斷言（blocker 1／major 179／minor 73）。最重的一條：使用者域八支寫端沒有「稽核落列失敗＝整筆不生效」案，而既有五個寫端域（角色、選單、IP 規則、授權歸檔、節流）都有。

**成因**：
- 追溯表的粒度是 task：需求只要被任一 task 引用就算覆蓋。被引用的 task 行常常只有實作描述（「稽核 `delete`」寫在流程句、測試段沒有對應斷言），或只有泛稱的「全量綠」。
- analyze 的覆蓋檢查以 ID 與關鍵字對映，對映到 task 不等於該 task 有斷言；兩層之間沒有任何機器面。
- 四種常見落差：①實作句被當成測試②CDP 排除清單（刻意分岔表、請求次數維度）把 rev6 獨有行為整列免判③一次性走查成為回歸面唯一承載④「兩負一正」之類簡稱未定義是哪兩負，各消費點各自理解。

**處置**：
- user 2026-10-06 核可全部套用、與本檔同顆落地：253 個缺口子句逐條補句（84 段、涉 45 支 task），附在 task 行原句之後（不拆原句）；每條補句以逐字錨回掛其子句。
- tasks.md「需求追溯」節改為子句表（子句 × 承載 task × 斷言類別 × 該 task 行內逐字錨 × 測試名），單一住處、無鏡像；全程紀律增「★子句層驗收」（各單元規格對照審查逐子句指出測試函式名或 DoD 命令實得，找不到即 blocker）；T110 改為逐子句核，不以 task 勾選代之。

**晉升面**：none——子句層追溯是否擴為 RULES 通則，留 007 刀收刀前由 user 裁定（T110 已排入提請）。

**再犯面與守法**：
- 「需求有對到 task」不是「需求有斷言」。判讀覆蓋率時，逐子句要求 task 行內的逐字錨，且錨須屬上述五種斷言之一；實作描述、泛稱全量綠、CDP 只觀察項、contracts 有案而無 task 指派，都不算。
- 逐字錨以機器核：quote 必須是該 task 行的子字串；既有測試以 `git grep` 核 `fn`／`def` 實存。agent 轉述的引文不算證據。
- 補句一律附在完整原句之後；改寫原句用整句替換，並重跑追溯表、找出被拆斷的錨。
