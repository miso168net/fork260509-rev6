LL-00058｜新增型圈界塊與修改型落在同一個 difflib 變更塊時，拔掉 START／END lint 照綠；以前代標記實數作預估，連帶把前代不承重的圈界算了進去（006 刀 U12）

**徵狀**：006 刀 U12 兩顆授權彈窗照 rev5 HEAD 的塊形落圈界，menu 7 塊、button 3 塊，即 ADR-00063 決定二的預估值。實跑 §1.5「逐塊拔 START／END → fork-delta-lint 必報未圈界新增」：menu 7 塊只有 2 塊轉紅，button 3 塊有 1 塊照綠。

規格對照 fix 把可移位的塊移開（menu 4 塊、button 1 塊）：
- 宣告類移到前後皆為未改行之處；
- 每次開啟先清狀態的兩行，移到呼叫端 `init()`。

只剩 menu getHome 內 await 之後的世代比對無處可移。碼品質 fix 撤掉它的圈界，改由所在修改型標記涵蓋。menu 新增型塊數因而為 6，與預估 7 不等；依 ADR-00063 翻案觸發器第三條停手，由 user 定 PATCH 時點。

**成因**：
- 一、lint 的判定機制。`tools/fork-delta-lint.py` 之 `find_unmarked_additions` 以 difflib 變更塊判定未圈界新增；含被移除碼行的變更塊整塊跳過（docstring 所載已知可接受殘留①），塊內新增行一律歸修改型標記涵蓋。圈界若與修改型落在同一變更塊，START／END 便無鑑別力。
  - 只隔空行或收尾大括號往往隔不開：lint 取差異用 `difflib.unified_diff`，比對檔達 200 行時 autojunk 啟發式啟動，空行、`}` 這類高頻行被當成 junk、不作對齊錨點（menu 彈窗 259 行即此形）。
  - 函式本體的基線行全數被替換時，其內任何位置都隔不開。
- 二、預估值的來源。預估取自 rev5 base-web 的標記實數。rev5 的 getHome 世代比對圈界，是後一刀補入時的落法，本就不承重；前代實數沒先過拔標記判定就拿來當預估。

**處置**：
- 可移位的塊，移到前後各有未改非空基線行包夾之處，移後逐塊拔標記皆紅。起手清狀態移到 `init()` 與原位時序等價：被移出的函式只由 `init()` 呼叫，兩處落在同一同步段、讀請求發出之前。
- 無處可移的塊撤掉圈界，改由所在修改型標記涵蓋，理由句補明。同檔 getChecks 的同型守衛本來就是此形。
- 出口計數照實數記；預估值延至收刀前 PATCH 實數化（user 2026-10-04 親決）。

**晉升面**：none——判準住 lint 本體與拔標記必紅之出口斷言，守法寫進本檔與後續單元定義。

**再犯面與守法**：
- ①落新增型圈界前先判擺位：塊的前後各須至少一條未改的非空基線行，與任何修改型改動隔開。整段被替換的函式本體內不放圈界——隔不開，就改由修改型涵蓋。
- ②每塊落地即做一次拔 START／END 必紅，不等單元出口才做。照綠就改擺位，或改歸修改型。
- ③以前代標記實數作預估時，先在前代形上跑同一拔標記判定。不承重的圈界不計入預估，或於預估依據註明。
