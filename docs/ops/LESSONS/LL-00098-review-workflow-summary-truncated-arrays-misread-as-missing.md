LL-00098｜手寫 review workflow 把送給下游評審之改稿陣列截斷而未標明：完整性評審以截斷後之清單判「lens 改稿漏項」，產出兩組與反駁定稿重複之合併稿與兩則覆議（008 刀 `/speckit-analyze`；2026-10-21）

**徵狀**：008 刀 `/speckit-analyze` 之手寫 workflow（九 lens→逐 lens 反駁→完整性評審）中，送給評審之摘要以 `fixes.slice(0, 6)` 只帶每筆改稿之前 6 項，且未註明原筆數。評審據此判 coverage#0（9 項）漏改 FR-063／FR-064／FR-066 三列、order-par#0（7 項）漏改 T126，各補一組合併稿（K22、K23）並出兩則覆議。實際上被截掉的第 7～9 項正是那幾處。主線套用前以「原檔區段重疊」檢核發現 K22／K23 與反駁定稿改同一段文字，改採反駁定稿、略去兩組，未誤套。

**成因**：摘要函式為壓低評審輸入長度而截陣列，但只在總長逾上限時才 `log()` 截斷；陣列層截斷是常態、payload 內沒有任何標記，下游 agent 無從分辨「沒有」與「被截掉」。

**防法**：給下游 agent 之摘要不截陣列；必須截時同筆附原筆數欄與「已截斷」字面，prompt 明告截斷規則。主線套用多來源改稿前，一律以原檔區段重疊檢核合併稿與各來源改稿（本次即此檢核接住）；評審之「漏項」主張先回原始 journal 核對全量再採。
