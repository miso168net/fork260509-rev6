LL-00054｜dev VM 的牆鐘每 30 秒被往回撥約 1.85 秒——同一行程內依序取兩次 `Utc::now()` 後者可早於前者、redis 以牆鐘換算之 TTL 可讀出大於設定值；以牆鐘兩點比序之測試斷言因此偶發紅（006 刀 U1、U5）

**徵狀**：`handler::throttle` 測試模組之 `unlocking_a_target_that_is_not_locked_still_audits_and_marks` 於 006 刀 U1 與 U5 之全量各紅一次（「標記時刻 … 須為解鎖當下」），其間五次全量未重現。主線以容器內同一測試 binary 連跑該案 700 次，紅 3 次：兩次是時刻斷言，一次是同一 helper 之 redis TTL 上界斷言（「標記存活期須＝窗長上界」）。三次的失敗時刻都正好落在時鐘探針所記或依其週期推得之回撥上。

**成因**：宿主 kernel log 有逾兩千筆 journald「Time jumped backwards」，間隔集中在二、三十秒。主線以探針每 20 毫秒取「牆鐘減單調鐘」之差（門檻 5 毫秒），實測得每 30.0 秒恰一對回撥（約 −0.8 秒、相隔 0.3 秒再 −1.05 秒），此外無他跳動。容器與宿主共用同一 VM 時鐘，故測試行程、postgres、redis 同受影響。受影響之 helper 斷言「解鎖前取之 `since` ≤ 標記時刻 ≤ 斷言當下之 `Utc::now()`」，並斷言 redis `TTL` 不逾設定值；時鐘在兩次取值之間回撥，前者便可大於後者。秒級取整時，只要回撥跨過一個整秒邊界就會紅，回撥量不必達一秒。redis 依牆鐘記到期時刻，回撥後讀到的 `TTL` 會多出回撥量。

**處置**：受影響 helper（`assert_marker_written`）的兩條斷言各放牆鐘回撥餘裕（5 秒；常數 doc 指本檔）：時刻區間兩端各放寬、`TTL` 上界放寬，下界與「值須為正規十進位字串」照舊。修前以容器內同一測試 binary 連跑該案 700 次紅 3 次（`TTL` 上界 1、時刻 2）；修後同法 700 次零紅，同時段探針記得 10 對回撥（回撥照常發生）。

**晉升面**：code——餘裕常數與其 doc 落在受影響測試件內，未立規則句。

**再犯面與守法**：凡以牆鐘取兩點比序的測試斷言，都須放回撥餘裕，或改以單調鐘量測。這包括 app 內兩次 `Utc::now()` 互比、app 時刻與 DB `now()` 或 redis 時刻互比、redis `TTL` 上界。餘裕取實測回撥量之上，目前 5 秒。偶發紅若帶時刻字樣，先查 `dmesg | grep 'Time jumped backwards'`，再以 20 毫秒取樣的探針量「牆鐘減單調鐘」之跳動，不必先懷疑受測碼。回撥頻率屬環境現況；換機或時鐘修正後可能消失，但斷言的寫法不應依賴它消失。
